# HR-помощник ТИУ — объединённый проект

Результат объединения двух проектов:

- **backend** — FastAPI: ИИ-ассистент (локальная GGUF-модель + RAG на Qdrant),
  база знаний, генерация кадровых документов, мессенджер, новости, уведомления
  (SSE + Web Push), контур персональных данных, админка и аудит.
  PostgreSQL + Qdrant.
- **Tyuiu.bot-main** (оставлена как эталон) — Next.js-приложение, из которого
  взяты основа фронтенда, дизайн-система и стили.

## Структура

```
HR helper combined/
├── app/           # Next.js 16 — всё приложение: UI, API, ML-контур
├── backend/            # FastAPI — исходник переноса; в работе не участвует
├── docker-compose.yml  # PostgreSQL + Qdrant
└── Tyuiu.bot-main/     # исходник-эталон фронтенда (можно удалить)
```

Перенос завершён: приложение целиком работает на Next.js, Python не запускается.
Каталог `backend/` остаётся как эталон — по нему сверялось поведение. Запускать
его больше нельзя: после перехода БД на UUID-ключи (см. «База данных») старый
код со схемой несовместим. Из утилит там актуальна только
`fix_document_paths.py`; `migrate_to_postgres.py` (SQLite → PostgreSQL) создаёт
прежнюю схему и устарел.

## Архитектура

Одно приложение на Next.js 16 (App Router): страницы, 111 обработчиков API,
RAG и локальная LLM в одном процессе, плюс отдельный worker для фоновых заданий.

- Авторизацию страниц делает `app/proxy.ts` (Next 16: бывший middleware)
  по наличию cookie; protected API сам отвечает 401.
- Realtime: `GET /api/events` (SSE) подключается в layout и раздаёт события
  страницам через DOM CustomEvents `hr:*` (как в исходном `scripts.js`).
- Стриминг ответа ассистента: `POST /api/chat/stream` читается через
  `fetch` + ReadableStream (`app/lib/api.ts → postSSE`).
- PWA: `app/public/sw.js`, `manifest.webmanifest`, офлайн-страница, Web Push.

Старые Jinja-шаблоны и `static/js` бэкенда не удалялись — они служат эталоном
при сверке поведения, но приложением не используются.

## Запуск

Всё поднимается одной командой:

```powershell
.\start.ps1
```

Если PowerShell отвечает «выполнение сценариев отключено в этой системе»,
запускайте через `start.cmd` с теми же ключами (`.\start.cmd -NoLlm`) или
двойным щелчком: он обходит политику только для этого запуска. Разрешить
локальные скрипты насовсем: `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`.

Скрипт проверит окружение, поднимет PostgreSQL и Qdrant, применит миграции БД,
соберёт фронтенд и запустит два процесса в отдельных окнах. Открывать —
**http://localhost:3000**.

| Ключ | Что делает |
|---|---|
| `.\start.ps1` | боевой режим: собранный Next.js |
| `.\start.ps1 -Dev` | режим разработки с горячей перезагрузкой |
| `.\start.ps1 -NoLlm` | без локальной модели — старт за секунды, ответы-заглушки |
| `.\start.ps1 -SkipBuild` | не пересобирать фронтенд |
| `.\start.ps1 -OpenFirewall` | открыть порт 3000 для домашней сети (от администратора) |
| `.\start.ps1 -Stop` | остановить всё |

Что именно запускается:

- **Next.js :3000** — всё приложение, включая ИИ-ассистента; сюда и заходить;
- **воркер** — фоновые задания: автоудаление ПДн, обновление веб-источников,
  контроль актуальности документов, возобновление зависших индексаций.

Python не запускается: приложение от него не зависит. Это проверено прямым
прогоном при остановленном FastAPI — страницы, API, чат с ассистентом,
генерация документов и построение схем процессов работают (31 проверка, 0 сбоев).
Прежний флаг `-WithPython` (старый бэкенд рядом, для сверки ответов) отключён:
с нынешней схемой БД FastAPI несовместим, и скрипт откажется его поднимать.

Первый ответ ассистента занимает около десяти секунд — модель (~4,6 ГБ)
загружается в видеопамять. Дальше ответы идут за считанные секунды.

Если что-то нужно поднять вручную:

```powershell
cd app; npm run start     # :3000  (или npm run dev)
cd app; npm run worker    # фоновые задания
```

### Конфигурация

Рабочий файл — `app/.env` (`DATABASE_URL` в формате Prisma
`postgresql://…`, `SECRET_KEY`, `CRON_SECRET`, настройки LLM). `backend/.env`
читает только утилита `backend/fix_document_paths.py`.

Видеокарта с небольшой памятью (4 ГБ): `LLM_N_GPU_LAYERS=auto` вместо `max`,
`LLM_VRAM_PADDING_MB=1024` (запас под буферы CUDA — без него генерация падает
с `ggml-cuda.cu: CUDA error`) и `LLM_MAX_CONCURRENT=1`.

## База данных

PostgreSQL 18 в Docker (`docker-compose.yml`). Схема описана в
`app/prisma/schema.prisma`, изменения ведутся миграциями Prisma Migrate
(`app/prisma/migrations/`). `start.ps1` применяет их сам; вручную:

```powershell
cd app
npx prisma migrate deploy   # применить миграции
npx prisma studio           # посмотреть данные в браузере
```

**Ключи — UUIDv7.** Все первичные ключи генерирует сама база (`uuidv7()`,
появилась в PostgreSQL 18). UUIDv7 начинается с метки времени, поэтому
сортировка по id совпадает с порядком создания — на этом держатся курсоры
ленты сообщений и отметки прочтения (`compareIds` в `app/lib/ids.ts`).
API принимает и отдаёт id строками; неверный id в пути даёт 422 `uuid_parsing`.
Адрес чата с ассистентом — `/chat/{dialogue_id}`.

**Нормализация до 3НФ** — что изменилось по сравнению со схемой SQLAlchemy:

- `poll_votes` без `poll_id` (опрос определяется вариантом ответа); опросы
  мессенджера и новостей сведены в одну пару таблиц `polls` / `poll_options`;
- `chat_sessions` влита в `dialogues`; `session_documents` → `chat_attachments`
  (составной внешний ключ не даёт прикрепить файл к сообщению чужого диалога);
- JSON-списки заменены таблицами: `user_messages.hidden_for` →
  `user_message_hidden`, теги документов → `kb_document_tags`, вложения новости →
  `news_media.attachment_order`;
- `messenger_reads.peer_key` (строка вида `u5`) → `peer_user_id` с внешним ключом;
- цикл `template_categories.default_template_id` ↔ `doc_templates` → флаг
  `doc_templates.is_default` и частичный уникальный индекс (не больше одного
  шаблона по умолчанию в категории);
- атрибуты группы FAQ вынесены в `faq_groups`;
- `my_documents.template_key` → `generator` (enum) + `template_id` (внешний ключ);
- `kb_sources.last_status` вида «error: текст» → статус `crawl_status` + `last_error`;
- `chat_feedback` — одна оценка на сообщение (ключ `message_id`), автор
  определяется через диалог.

Строковые справочные значения стали enum-типами, время — `timestamptz`.
CHECK-ограничения, частичный индекс и `NULLS NOT DISTINCT` дописаны в SQL
миграции вручную: Prisma их не описывает, но и не удаляет.

Флаги прав `users.is_admin`, `is_kb_editor`, `can_access_pii`, `is_active`
оставлены отдельными колонками: это независимые права, которые комбинируются, а
не взаимоисключающие роли, поэтому 3НФ они не нарушают.

Намеренно без внешних ключей: JSON-снимки (`chat_messages.sources`,
`fields_schema`, варианты и `doc_refs` FAQ) — это история показанного, а не
ссылки; метки-«водяные знаки» `variant_group`, `memory_covers_up_to`,
`last_read_id`; `pii_audit.entity_id` — журнал должен пережить удаление объекта.

**Время.** API отдаёт даты в ISO с `Z` (`isoUtc` = `toISOString()` в
`app/lib/db.ts`), поэтому интерфейс больше не сдвигает время на часовой пояс.

**Перенос данных со старой схемы** (выполнен один раз, порядок — в шапке
`app/scripts/migrate-legacy-db.sql`): старая база восстанавливается в схему
`legacy`, SQL-скрипт переливает данные в новые таблицы (UUIDv7 строятся из
`created_at`, так что хронология сохраняется; ссылки `/kb/documents/N`,
`/news/media/N` внутри текстов и JSON переписываются на новые id), затем
`app/scripts/migrate-legacy-qdrant.mjs` переводит `document_id` в Qdrant на
UUID и удаляет кэши, завязанные на старые id. После переноса старые сессии
недействительны (cookie хранила числовой id) — пользователи входят заново.

## Этап 2 — перенос бэкенда на Next.js (завершён)

### Как устроена миграция

Переносили по одному домену за раз (strangler-паттерн), приложение всё время
оставалось рабочим. Два условия, которые это обеспечивали:

1. **Общая база.** Оба бэкенда работали с одним PostgreSQL. Схема создавалась
   SQLAlchemy-моделями Python, Next.js читал её через Prisma (`db pull`), перевод
   со старого SQLite делал `backend/migrate_to_postgres.py`. После переноса схема
   перешла под Prisma Migrate и была переделана (см. «База данных»).
2. **Общая сессия.** `app/lib/session.ts` читает и пишет ту же cookie
   `hr_session` в формате Starlette (itsdangerous: HMAC-SHA1, key derivation
   `django-concat`). Вход через Next.js был виден FastAPI и наоборот — при
   переносе очередного домена пользователи не разлогинивались.

Тонкость: Next прогоняет значения cookie через `encodeURIComponent`, из-за чего
завершающие `=` в base64 превращались в `%3D` и Starlette такую сессию не
принимал. Поэтому заголовок `Set-Cookie` формируется вручную
(`serializeSessionCookie`), а не через `cookies().set()`.

Вторая тонкость — на случай, если правила проксирования понадобятся снова.
Они обязаны возвращаться из `rewrites()` как объект с ключом `fallback`, а не
голым массивом. Массив попадает в `afterFiles` и срабатывает **до** динамических
маршрутов, поэтому `/api/dialogues/12` не находил обработчик
`app/api/dialogues/[dialogue_id]` (проверка файловой системы ищет путь буквально)
и уходил в FastAPI — то есть перенесённый код молча не вызывался. `fallback`
проверяется после динамических маршрутов и работает как задумано.

Сейчас в `next.config.ts` правил проксирования нет вовсе: все 118 путей FastAPI
покрыты, а прокси при выключенном Python лишь превращал бы честный 404 в 500.

### Что перенесено

Всё. На Next.js — **111 обработчиков**: авторизация, новости, уведомления,
админка, аудит ПДн, диалоги, Web Push (включая саму отправку), база знаний,
контур персональных данных, мессенджер с каналом событий, чат с ассистентом
(RAG + локальная LLM), парсеры всех форматов, генерация документов и
инструменты-мастера Б1–Б7, приведение схем процессов к единому виду,
просмотрщик документов, фоновые задачи.

**Не переносится только одно — WebSocket `/api/messenger/ws`.** Обработчики
маршрутов в Next не умеют выполнять protocol upgrade: это ограничение
платформы, а не недоработка. Практических потерь нет — HTTP-путь для индикатора
набора текста и отметок о прочтении работает и использовался как запасной ещё
в исходном приложении.

Эквивалентность проверялась сравнением ответов обоих бэкендов на одинаковых
данных: они работали с одной базой, поэтому JSON сверялся поле в поле.
Дополнительно: autofill сверен с Python на всех 17 реальных бланках, схемы
процессов — 8 из 9 SVG байт в байт, просмотрщик документов — 93 из 103 случаев
(расхождения только в поле `content` для `.rtf`/`.doc` и происходят из парсеров),
результаты инструментов — побайтово.

Со стороны интерфейса перенесены и мелочи, которые легко упустить: счётчик
непрочитанных ответов с автопометкой по видимости, сворачивание боковых панелей,
прогресс-бар загрузки файла, встроенный редактор картинок в новостях (поворот,
обрезка, масштаб), сохранение черновика карточки ПДн при истечении сессии,
быстрое меню приоритета документа, предпросмотр вложений мессенджера, модалка
результатов голосования со склонениями, перетаскивание и изменение размера
плавающей панели мессенджера с закреплением, вынос мессенджера в отдельное окно
через Document Picture-in-Picture, свайп-закрытие тостов, аватары по полу.

### Исходная оценка переносимости (для истории)

Оценка делалась до переноса и в трёх пунктах оказалась **неверной** — фактические
результаты в разделе «ML-контур на Next.js».

| Компонент | JS-аналог | Вердикт (до переноса) |
|---|---|---|
| RAG-пайплайн (`services/rag`, 4483 строки: HyDE, декомпозиция запросов, self-check, семантический роутер) | нет | Переписывание с нуля с риском потерять качество. **Перенесено полностью.** |
| Локальная LLM, GGUF T-lite 8B (`llama-cpp-python`) | `node-llama-cpp` | Работоспособен, но требует пересборки биндингов. **Перенесено, работает быстрее оригинала.** |
| Лемматизация русского для BM25 (`pymorphy3`) | `node-lemmer` | «Единственное, чему нет полноценной замены». **Неверно:** Az.js работает на тех же словарях OpenCorpora — на проверке 12 лемм из 12 совпали с pymorphy3. |
| Эмбеддер + реранкер (`fastembed`, jina-reranker-v2) | Transformers.js / `@mastra/fastembed` | Переносимо: у jina-reranker-v2 есть официальные ONNX-веса с интеграцией Transformers.js. Но на CPU в Node будет медленнее. |
| OCR (Tesseract), конвертация (LibreOffice) | — | Это внешние бинари, вызываются одинаково из любого языка. Не проблема. |
| Распознавание PDF-сканов | — | «В Node не сделать». **Неверно:** у скана страница и есть картинка — её достаточно извлечь и передать в Tesseract. |
| Препроцессинг сканов (OpenCV deskew) | `sharp`, `opencv.js` | Переносимо, но переписывать вручную. |
| Извлечение текста веб-страниц (`trafilatura`) | `@mozilla/readability` | Переносимо с потерей качества. |
| Генерация .docx (`docxtpl`) | `docxtemplater` | Переносимо: в проекте только текстовые подстановки, бесплатной версии достаточно (картинки и HTML — платные модули). |

### Запуск фоновых задач

Периодические задания (обновление веб-источников, контроль актуальности
документов, автоудаление ПДн, возобновление зависших индексаций) в Next.js
не могут жить внутри веб-процесса — демона там нет. Поэтому они вынесены в
отдельный процесс:

```powershell
cd app
npm run worker      # рядом с npm run dev / npm start
```

Либо их можно дёргать внешним планировщиком (Windows Task Scheduler, cron):

```
POST /api/cron/web-sources
POST /api/cron/documents-freshness
POST /api/cron/pii-cleanup
POST /api/cron/resume-indexing
```

Эндпоинт закрыт секретом `CRON_SECRET` (заголовок `X-Cron-Secret` либо
`Authorization: Bearer`). Без него — 401.

Планировщик в Python выключен (`SCHEDULER_ENABLED=false` в `backend/config.py`)
ещё со времён переноса, когда оба бэкенда работали одновременно: иначе задания
выполнялись бы дважды. Сейчас FastAPI не запускается вовсе.

### ML-контур на Next.js

Перенесён полностью: эмбеддинги, векторный поиск, BM25, реранкер и локальная
LLM работают внутри Next.js (`app/lib/ml/`).

**Векторы совместимы — переиндексация не нужна.** FastEmbed на стороне Python
использует ONNX-сборки `xenova`, то есть ровно те, что грузит Transformers.js.
Сверка показала косинус 1.000000 и нулевое расхождение после нормировки, так
что существующая коллекция Qdrant (2553 точки) осталась валидной. Разница лишь
в том, что Python отдаёт ненормированный вектор, а Qdrant с метрикой Cosine
нормирует сам.

**LLM.** `node-llama-cpp` грузит тот же GGUF-файл. Практические находки:

- **Значение `-1` для числа GPU-слоёв здесь не работает** — в отличие от
  llama.cpp, оно оставляет модель на процессоре. Нужно `max`
  (`LLM_N_GPU_LAYERS=max`), иначе скорость падает примерно в 50 раз.
- Бэкенд задаётся явно: `LLM_GPU_BACKEND=cuda`. Без этого выбирается Vulkan,
  который на NVIDIA заметно медленнее.
- Размер контекста задан как верхняя граница (`{max: N}`), а не жёстко: KV-кэш
  на 16k × несколько слотов не помещается в 12 ГБ вместе с весами, и загрузка
  падала с «CUDA out of memory».
- Пакеты с нативными бинарниками перечислены в `serverExternalPackages`, иначе
  после сборки модель молча не грузится и чат отвечает заглушкой.

**Параллельные генерации — преимущество перед Python.** `llama-cpp-python` не
потокобезопасен, поэтому в оригинале запросы к модели сериализованы одним локом.
`node-llama-cpp` держит несколько независимых последовательностей в одном
контексте и считает их параллельно в общем батче. Лимиты настраиваются:
`LLM_MAX_CONCURRENT` (одновременных генераций), `ASSISTANT_QUEUE_MAXSIZE`
(предел очереди) и `ASSISTANT_MAX_PER_USER` (анти-флуд); ожидающий запрос
получает свою позицию в очереди.

**Морфология.** Лемматизацию делает Az.js на тех же словарях OpenCorpora, что и
`pymorphy3`, поэтому токены BM25 совпадают. Порядок разбора в
`app/lib/ml/bm25.ts`: Az.js → стеммер Snowball → исходное слово.

**Парсеры.** PDF читает `unpdf`, сканы — Tesseract (страница скана и есть
картинка, её достаточно извлечь), старые форматы Office — LibreOffice. Внешние
бинари вызываются из Node так же, как вызывались из Python.

Отдельно — архитектурные ограничения самой платформы:

- **Планировщик.** `APScheduler` жил в процессе приложения; у Next.js такого
  процесса-демона нет. Поэтому — отдельный worker (`npm run worker`) или
  системный cron.
- **WebSocket.** Обработчики маршрутов не умеют protocol upgrade, поэтому
  `/api/messenger/ws` перенести нельзя. Мессенджер работает по HTTP-пути,
  который в исходном приложении был запасным.
- **SSE и присутствие.** Онлайн-статус выводится из открытых SSE-подключений в
  памяти процесса. Это работает только в одном инстансе: при горизонтальном
  масштабировании понадобится Redis pub/sub. Ограничение было и в Python
  (uvicorn запускался без `--workers`).
- **Состояние добора полей при генерации документа** держится в памяти, но
  каждая мутация сбрасывает снимок в таблицу `app_state` (PostgreSQL), а на
  старте сервера он поднимается обратно (`lib/docs/docgen.ts`,
  `lib/state.ts`) — рестарт диалог «уточни должность и оклад» больше не
  теряет. Осиротевшие после рестарта генерации закрываются пометкой
  (`recoverInterruptedStreams` в `lib/chat.ts`), BM25-индекс поднимается из
  дискового кэша (`docs/.cache/bm25-chunks.json`). При нескольких инстансах
  Node состояние по-прежнему не общее: снимок читается один раз на старте.
- **Долгие LLM-запросы.** При self-hosted (`npm start`) таймаутов нет. На
  serverless-хостинге вроде Vercel генерация на минуту-две упрётся в лимит и
  потребует очереди с фоновым worker'ом.

**Итог:** исходная оценка была осторожнее, чем следовало. Полный отказ от Python
оказался возможен без потери качества русскоязычного поиска: лемматизация
сохранена (Az.js на словарях OpenCorpora), векторы совместимы, а локальная
модель на `node-llama-cpp` считает ещё и параллельно.

### Обслуживание

**Пути к файлам в базе — абсолютные.** Если каталог проекта переименовали или
перенесли, документы перестают открываться: приложение отвечает «Доступ к файлу
запрещён» (путь оказался вне `docs_dir`) или «Файл не найден», хотя файлы на
месте. Чинится скриптом:

```powershell
cd backend
python fix_document_paths.py           # показать, что изменится
python fix_document_paths.py --apply   # записать
```

Он переносит пути внутрь актуального `docs_dir`, сохраняя структуру после
каталога `docs`, и пропускает записи, для которых файла нет на диске.

### Что починено после ухода Python

**Даты без метки часового пояса — исправлено.** Старый бэкенд сериализовал UTC
через `.isoformat()` без суффикса `Z`, браузер читал такую строку как локальное
время, и отметки промахивались на часовой пояс (для Екатеринбурга — на 5 часов).
На время переноса Next.js намеренно повторял это поведение; теперь `isoUtc`
отдаёт `toISOString()`, а колонки времени стали `timestamptz`.

**FAQ-контекст не доходил до модели** — исправлено: в `lib/ml/pipeline.ts`
FAQ-контекст собирается и попадает в промпт (в Python `pipeline.py:1459`
присвоение стояло после `return` и было недостижимо).

**Тесты.** Автотесты генераторов документов: `cd app; npm test`
(node --test + jiti, без БД/LLM/Qdrant, `scripts/tests/`).

**Линтер ругается на 37 мест** (`react-hooks/set-state-in-effect`, `refs`,
`immutability`). Это правила нового React-плагина, срабатывающие на рабочих
паттернах — загрузка данных в `useEffect`, «latest ref», императивная правка
DOM в contenteditable. Ни сборке, ни работе не мешают, но при спокойной
переработке страниц их лучше расшить.
